# 鼠王关 PCG：可解释评分、全地图进化与逐代回放长期开发计划

本计划依据 2026-11-20 确认的五阶段方案制定。2026-11-24 起，外壳布局进化采用 [§5.4 单亲档案方案](#54-phase-4-正式引擎与单种子验收)。[§5.2](#52-phase-4-准入与当前收口顺序)列出正式启动前的待办和锁定参数，[§6](#6-自动运行与最终交付)定义自动运行与归档。执行证据和提交见 [PROGRESS.md](PROGRESS.md)。

## 1. 研究目标与执行方式

完整数据流：**可变拓扑地图生成 → 几何／通路验证 → Depthmap 空间分析及 Godot 战斗模拟 → S/F/P/D 多目标评分 → 遗传进化 → Generation 0–20 离线回放 → Godot 物理验证。** 研究观察、射击、躲避、补给、重新交战、击败大型鼠王的战斗循环。轮廓或数值接近原图不自动代表体验更好；三种搜索方法不预设胜负。

五个 Phase 各为一项任务，拆为可验证功能模块。每模块先定义输入/输出/验收，复用或实现，再测试、必要运行验证、更新 `PROGRESS.md`、显式暂存并 Git Commit，然后继续下一个模块。阶段验收不过，不启动依赖该阶段的正式工作。保留已有未提交修改，不自动 push。大型实验输出留运行目录，Git 仅保存清单、哈希和小型证据；每阶段报告测试、限制、配置、来源及对应 Commit。

复用顺序：**现有实现 → 成熟开源模块 → 最小必要开发**。审查版本、许可证、依赖和测试，不整套无目的迁移。候选第三人称/射击组件为 [RoboBlast/godot-fps](https://github.com/mdtoupin/godot-fps)、[Kenney Starter Kit FPS](https://github.com/KenneyNL/Starter-Kit-FPS)；[LimboAI](https://github.com/limbonaut/limboai) 仅在潜行者状态管理确实需要时接入。本地现有移动、Boss追击、碰撞、挤身、破坏、Depthmap CLI、缓存、pymoo多目标选择、二维图表优先复用。

保留 Legacy、`evolution/runs/search_v1`、原 DXF、`shuwang.graph`。新战斗协议与旧逃生评价完全分版。新系统的 Python Layout 是唯一几何来源；二维预览、Depthmap 和 Godot 读取同一布局。所有正式评价由 Python 调度，DepthmapX 输出空间指标，Godot 按冻结协议执行批量战斗与物理验证；Codex仅编写、调试、检查证据与报告，不逐地图评分或决定遗传生存选择。程序须能在对话关闭后运行与恢复。

### 1.5 技术栈与工具复用规范

本项目优先采用下列技术栈。正式实施前先审查已有仓库、接口、测试与依赖，确认模块是否已存在。下表是默认选型和职责边界，不要求为了新增工具重构工程；工具安装不等于功能接通或阶段验收通过。

| 模块 | 首选工具 | 复用与接入要求 |
|---|---|---|
| 编程与调度 | Python | 复用现有任务、并行、断点与来源校验；本地程序可独立运行 |
| 多目标遗传算法 | pymoo + NSGA-II | 保留默认框架，复用非支配排序、拥挤度与约束选择；S/F/P/D独立选择，Q仅展示 |
| 可变拓扑 Genome | NetworkX + 自定义单亲编辑与修复 | 复用现有图与稳定 ID，逐项验证地图语义、几何和角色通行 |
| 几何生成与验证 | 现有Full-PCG实现；缺失能力优先使用Shapely | Python Layout是新系统唯一几何来源，不新建第二套随机布局 |
| 空间句法分析 | DepthmapX CLI | 复用现有调用、导出和缓存；保留命令、原始结果、单位、网格与版本 |
| 三维关卡与战斗验证 | Godot | 负责实际三维地图、碰撞、导航、视线、射击与战斗事件核验 |
| 交互式进化回放 | Streamlit + Plotly | Phase 4优先使用本地运行的Viewer，支持断网读取已有实验；复杂实验分析UI不全部放入Godot |
| 遗传谱系可视化 | NetworkX，配合Viewer绘制 | 保留个体出现ID、父代、算子和内容哈希，不合并相同内容的不同出生记录 |
| 实验记录与缓存 | JSON + 按需接入SQLite | 兼容现有缓存，JSON保留原始证据与交换格式；SQLite优先作实验索引和查询，集中或短事务写入，不因采用数据库重算旧实验 |
| 自动测试 | 现有unittest + 按需接入pytest；Godot无界面测试 | 保留现有测试；pytest可作为统一运行入口，新功能按风险补充测试，不为换框架重写旧测试 |
| 版本管理 | Git | 逐模块验证后显式提交，保留用户修改，不自动推送 |

技术选型原则：

1. 优先复用已有实现，其次经过测试的成熟组件，最后最小必要自定义代码；不得因新增工具而重构整个工程。
2. pymoo为默认遗传优化框架；只有记录了明确无法满足需求的技术限制和复现实例，才评估DEAP等替代方案。
3. 用结构化 Genome 实现单亲编辑和拓扑修复，沿用房间、门、走廊和战斗约束。
4. Evolution Viewer优先采用Streamlit + Plotly，并与后台实验解耦；关闭Viewer不应终止搜索，刷新页面不应重复启动任务或评价候选。
5. Godot主要负责实际三维地图与机制验证，Python负责实验调度和批量计算；采样验证范围按冻结协议明确，不把Python代理结果当Godot实测。
6. 所有正式工具记录实际版本、配置、依赖、来源与许可；锁定可复现环境，新增工具须先验证兼容性，不静默升级或降级旧实验依赖。
7. Phase 1验收必须输出当前仓库实际使用的工具清单，以及每项新增依赖的必要性、接入阶段、替代方案和兼容性证据。复用已有Phase 1.1审查并补充缺项，不重做已通过模块。
8. 评分公式由项目独立实现并保持可复算；成熟工具负责测量、模拟、优化、存储和展示。工具接入不替代评分校准、反例测试与实际玩法验证，不得改变已冻结实验的评价口径。分别报告公式计算正确性、测量/模拟一致性和体验评价有效性。

2026-11-20修订：补充技术栈与复用规范；不改变五阶段门槛、6048请求预算或S/F/P/D评分协议。新增依赖先完成兼容性检查，按所属阶段接入；安装本身不推进Phase。

## 2. 数据合同与战斗口径

接口：`generate(genome, config) → Layout + ValidationReport`；`analyze(layout, config) → SpatialResults`；`simulate(layout, combat_config, seed) → EpisodeLog`；`score(layout, spatial_results, logs, scoring_config) → ScoreReport`；`load_layout(layout) → Godot 2D/3D`。

Genome含稳定房间ID、功能、局部轮廓、位置、旋转、连边、普通/through/break/window通道、障碍、同场出生和补给位置。Layout含实际房间/走廊多边形、地板、墙、Portal、遮挡、出生、拓扑实现映射。Individual出现ID与内容哈希分离；保留父代、算子、修复、评价。Generation分别保存新子代和选择后的全部种群、当前/累计Pareto、展示代表与各目标历史最优。坐标为Godot X/Z模型米；Depthmap图纸单位转换显式记录。日志含版本、配置/来源哈希，原始事件、时间、位置、视域、射击/伤害、换弹、拾取、破坏、分裂和终止状态。评分器与模拟器分离，能凭原始日志复算。

玩家与大型鼠王在**同一黄色主廊/转接区（hall优先，或foyer）的真实连续核心空间**出生，ID相同但位置和朝向不同。核心空间面积在功能房间前25%，全开时连接至少3邻区，初始至少2条玩家可用离开路径；按合法路径和攻击时序验证开场反应余量。核心区不必在几何中心；当前外壳分区方案可保留原图空间关系作为设计先验，但不要求精确复刻外轮廓。固定武器、血量、速度、角色尺寸、攻击与分裂阈值，不让遗传算法调整角色强弱。初始弹药、总补给及包数固定，仅补给位置进化，拾取耗时、不刷新。

胜利=大型鼠王死亡；失败=玩家死亡；超时独立记录，出口只作战后离场标记。Boss低于固定血量阈值后分裂潜行者，后者潜伏、接近、预警攻击、造成伤害与短暂控制、撤退；其速度与单次伤害在人工试玩 Inspector 中可调，正式评分冻结时锁定固定值且不进入遗传基因。本轮不生成原作后续独立潜行者终战场地。through玩家按A挤身、Boss耗时撞开；break仅Boss破坏，之后双方可通过；window为独立通道类型：玩家交互翻越，可从窗口开口射击；Boss不得翻越或撞开，窗框/窗台仍参与相应高度的视线与弹道遮挡。block是障碍而不是连接。感知严格区分Depthmap潜在可见性、玩家相机实际视域和枪口弹道；双方不能透视未知位置。二维代理用固定seed进行廉价评价，Godot核对实际碰撞、LOS、导航、射击和状态事件。首版无需完整动画、美术、复杂UI或完整游戏武器库。

### 2.1 战斗事件顺序与边界合同

Phase 1.4先明确同一逻辑步内感知、射击/伤害、Boss分裂、双方死亡、拾取、换弹、门破坏和胜负/超时的处理顺序及同时间戳裁决。Phase 2实现事件序号、逻辑步与状态转换日志，Phase 3按同一合同核对Python与Godot；不得依赖两个运行环境各自的回调顺序。

边界样例至少覆盖：一次伤害同时跨过分裂阈值和零血量、双方同一步死亡、死亡与拾取同时发生、换弹完成与射击同一步、门破坏前后的命中与穿越、胜利与超时同一步。各样例记录输入、事件顺序、预期状态与原始日志。

当前评分核拒绝未实际经历第二阶段的胜利局。2026-11-21已确认并在Phase 1.4处理：首阶段跨阈值命中夹断到分裂阈值，丢弃超额伤害，后续逻辑步第二阶段才可击杀；零时长第二阶段不能计胜利。Phase 2/3继续验证Godot和Python的实际事件一致性，不重开已解决的规则选择。

### 2.2 窗户、多Portal与协议迁移（2026-11-22）

接纳当前新增的window与同一对房间之间的多个门洞。每个Portal使用独立稳定ID，保留自己的端点、宽度、类型、交互状态与通行/视线/弹道几何；不能按房间对合并或丢掉第二扇门。基础拓扑用去重房间邻接，Portal层用带ID的多重连接；房间邻区数、核心区度数和基础非同构统计使用不同邻居数，多开门不直接增加这些值。Portal级环路/替代路线另列并以实际使用验证，不靠重复边刷D。

当前兼容性缺口必须先修复再验收：`combat_pcg/contracts.py` 的Genome仍只接收normal/through/break并拒绝重复邻接；仅对schema_version=5日志放行vault事件不等于Genome、代理和评分已支持新机制。Layout数字版本、Genome/事件协议、战斗配置和评分版本分别登记，明确适配与迁移；不自动改旧文件标签，不混用已有缓存。

window的翻越时长、交互范围、角色净空、可打断条件、失败恢复及窗框高度须进入共享配置与事件合同。当前Godot翻越时长0.65秒只是实现初值，未完成Python/Godot共同校准。分别定义玩家通行、Boss通行、实际视野和枪口弹道；Depthmap二维潜在可见性不得直接代表三维窗台高度的可见或命中。Phase 3冻结前确定并记录空间分析导出近似与限制。

window不能成为Boss无法反制的永久安全输出点；需用真实连通、敌人响应、射击与翻越风险反例核对。不得为通过旧验证而把window改成through或删除多门。

## 3. 全地图生成与合法性

原可变锚点图配置默认8–18个功能房，走廊和交叉口另记；当前外壳分区方案的房数口径见3.2节，不把旧配置范围直接套用为新方案已通过的门槛。原方案支持房间增删、边重接、环路增删、多个核心、支路、瓶颈、死路、捷径与绕行。through默认2–8、break默认1–5，按可用边限制。空间规则可配置，保留核心风险、遮挡、开放/压迫变化、可预测但不绝对安全的转移、破坏后的连通变化，而非固定11房模板。

几何层支持不同长宽比、矩形、削角、梯形、斜边、L形及凹口；独立位置/尺寸/45度旋转；使用多边形净距、确定性走廊A*、门洞边界定位和角色净空。未声明的走廊交汇、穿第三方房间、贴墙隐藏开口均无效；真实交叉口要显式记录。修复最多8轮，失败保留原因，不退回固定模板。地板、墙、碰撞、障碍和两角色导航取自同一轮廓。基准可玩面积0.75–1.25倍，必须先统一扣墙/障碍/开口口径。

廉价过滤先于Depthmap：多边形/墙/门合法、房间无非预期重叠、实际几何图与目标拓扑一致、角色净空与出生合法、初始/全开/代表破坏中间状态、Boss可逐步到达撞击面、全开后必要区域对双方可达、无短路和异常绕行。再区分战斗可行性：有反应、射击、资源与反制证据。几何 INVALID、战斗 UNCERTAIN、系统 ERROR 分别记录；12局未获胜不证明地图不可能获胜。

100 个固定 seed 的工程目标为几何／拓扑合法率至少 80%，合法样本至少有 5 种房数、10 类精确非同构基础拓扑、3 种环数，并包括旋转和非矩形空间。报告完整的尝试、修复和失败。允许变量见 §3.3.2。后续每个子代从一张亲代布局进行局部编辑或区域重排，pymoo 用于复用非支配排序、拥挤度与约束选择。

### 3.1 生成、修复与算子多样性审计

在已有100seed审计和代史基础上，分别报告修复前/后的房数、环数、精确非同构拓扑类别、布局重复率、合法率、修复次数与幅度；区分提案、修复结果和最终幸存种群，避免只报告筛选后的多样性。几何尚未构成时记录可获得的Genome统计，缺项明确标记，不伪造几何值。

按局部编辑和区域重排分别报告尝试、成功、失败、修复及实际变化，并报告亲代抽样集中度和后代请求数。固定旋转／平移不变性和近似布局比较口径，分别统计拓扑同构、Genome 重复和 Layout 重复。B/C 使用相同的生成约束和修复规则。无效与重复请求照计预算。多样性坍缩诊断与补救须在正式冻结前验证。

### 3.2 当前外壳分区方案与旧生成器的关系（2026-11-22）

当前Main使用 `scripts/shell_main.gd` 调用Python `full_pcg/shell_layout.py`，运行时加载同一Layout到Godot战斗白模。这是当前开发与后续验收的对象，不仅是辅助展示；不得按过时交接自动退回旧锚点生成器。旧 `topology.py/geometry.py` 可变锚点图及其已验收证据继续保留，复用底层模块，不并行重做当前方案。

外壳分区保留左右翼、主廊、柱周绕行等设计先验，同时允许外壳尺度/转折、内部房间分割、门型/位置等变化。这是有约束的生成族，不宣称任意图或任意外形自由生成。房间内净尺寸以 `room_limits.py` 所用DXF内墙坐标证据为参考；记录墙厚、凹形可用尺寸、尺度未实机标定及人工确认分区的来源/哈希。人工reviewed种子属于开发证据，不能冒充独立未见测试。

当前已有shell审计观察到7–11个房间；这是现有样本范围，不等于正式配置已锁定。Phase 2须显式写出该方案的功能房/主廊计数口径、房数允许范围、变异能力及面积/净尺寸限制，然后重新按固定100seed验证。保留>=80%合法率、至少5种房数、10类基础非同构拓扑和3种环数的多样性目标；不能把旧锚点90/100、旧同场98/100或不同shell审计的最好数值合并为新验收。多Portal去重后的拓扑、玩家/Boss通路及实际机制须分别报告；不通过则记录限制，不静默降低门槛。

Phase 3在这一明确的生成族与新通道协议上校准、验证并冻结，不负责把当前地图重新改造成原方案。Phase 4前补齐该生成族可保存/重建的Genome与合法算子；仅按seed随机生成和人工审图不等于完成遗传优化。Phase 5的B/C须使用同一已冻结生成族和分布；A若不能适配同样的window、多Portal及战斗条件，应明确不可比，不直接沿用旧逃生分数。

### 3.3 遗传进化允许的结构变化与保护规则（2026-11-22）

本节按用户引用对话 `01a1df6a-7d7d-7233-90be-823038a67e2b` 中后续布局修订确定，较新的直接要求优先于早期草案：取消80%双端/20%自由布局，所有候选遵循完整外壳→长廊→左右翼内部细分。证据与当前实现位置见 [结构规则来源记录](reports/combat_v3/STRUCTURE_RULE_SOURCES.md)。以下是设计约束，不是由单局路线推导的普遍玩家规律；不锁死原始11个凸分区、原图每一顶点或单局玩家路线。

#### 3.3.1 必须保护的空间关系

| ID | 结构限制 | 可检查的条件 |
|---|---|---|
| H01 | 先完整建筑，后内部细分 | 外壳为合法连续多边形；室内分区覆盖同一外壳；共墙只记一次，无叠房、窄夹缝、外接走廊串珠或隐藏连接 |
| H02 | 全部候选保留长廊连接左右绕行区 | 分别标记主廊、转接区和左右翼；真实廊带连续，并实际连接两翼；不得为生成多样性恢复20%自由布局、删除一翼或用一排小房冒充长廊 |
| H03 | 长廊具备长段和转移作用 | 按净长度/中位净宽检查主长段，当前设计门槛>=3；入口可放宽，允许转折/斜接和局部宽度变化；不得新增未声明跨翼连接绕过主廊，破坏后变化也需记录 |
| H04 | 两翼均有实体净空下的绕行 | 左翼保留连续较大空间、绕柱/偏置隔墙转移；右翼保留隔墙/侧室及实际替代路线。绕柱或经不同门绕墙返回均可，须记录见证路径，不用“图上有环”代替实测 |
| H05 | 出生限定黄色主廊/转接区 | 玩家和Boss必须在同一连续hall或foyer分区、不同位置，优先hall；保留核心区面积/不同邻区/初始离开路径和反应余量要求。不得通过变异迁到左翼大房或分开出生 |
| H06 | 小房满足原DXF净尺寸参考 | 扣墙后使用实际内部可容纳矩形/净宽验证，不能只比面积或包围盒。两类参考为north约3.19139×2.29381模型米、east_low约3.50591×1.79154模型米；按对应房型或已声明通用选择匹配一类，不对所有房机械叠加两个长宽下限。凹形臂和盲条另查，不能靠大面积掩盖细长不可用尾部 |
| H07 | 声称为L形的嵌套大房必须是真L形 | 矩形母区角部切出矩形小间，大间为单一内凹直角的连续L形，两臂满足净宽；大小间恰好拼回母区。多凹角阶梯、狭长细条、居中挖洞不能冒称已确认L形。普通房不强制全为L形，L形也不强制每图出现 |
| H08 | 保护不同通道语义 | through是需挤身的半开门，窄缝不等于充分射击窗口；window可射击/翻越，Boss不能破窗或穿窗；break仅Boss撞开后双方通行。每个Portal独立ID和状态；不能删掉第二扇门或偷换类型通过检查 |
| H09 | block位于大空间较中央 | 以扣墙净面积较大房间作候选，几何净空中心而非凹多边形外的算术中心；偏移不挡门、不截断两角色必要通路并保留绕行。数量和尺寸不作为当前优化基因，只允许声明范围内位置变化 |
| H10 | 战斗和证据预算不由地图基因改变 | 玩家/Boss能力、两阶段击杀、弹药/补给总量固定，补给只变位置；所有改动由同一Python Genome/Layout重建，编辑器/二维/Godot一致，不能仅换seed掩盖无继承随机生成 |

开口的用户意图是“尽量两个，不要window作为唯一入口”。默认生成配置沿用当前实现：每个功能房至少两个有实体间隔的Portal，且至少一个normal或through；允许门洞+window、through+window、门洞+break、through+break等组合。两个开口可通向同一邻区，但不算两个不同邻区，也不自动等于两条独立安全逃路；break未撞开前不算玩家初始出口。若共享墙不足以放下两个安全开口，不强挖窄缝或穿墙链接；记录失败/诊断。此默认比用户“尽量”措辞更严格，作为可版本化配置保留，不冒称单局数据证明所有房必须双门。

| 对象 | 允许变化 | 边界 |
|---|---|---|
| 建筑外壳 | 两翼伸出位置、长度、进深、同侧/异侧展开、端部削角、局部外墙转折 | 保留H01–H04；外壳必须真的有差异，不把“保留形式”解释为固定全部外墙坐标；不要求保留原DXF每个转角 |

#### 3.3.3 单亲编辑与修复的保护顺序

1. Genome显式保存宏区身份、外壳参数、母区/嵌套关系、隔墙、Portal与角色/补给，使用局部坐标和稳定ID。声明当前采用哪类参数与操作范围；不把旧锚点算子直接套到shell。
2. **局部编辑（Diff Edit）。** 从一张亲代派生，每个子代目标为 1–3 个允许的小改动，例如平移门洞、移动隔墙、拆并小间或调整次要连边。记录受影响的房间、Portal 和宏区。
3. **区域重排（Full Edit）。** 在同一亲代内重新细分一个允许变动的区域，例如保留主廊接口并重新安排一翼的隔墙、角部小间和绕行。遵守外壳覆盖、共墙、净尺寸、主廊、同场出生和两翼结构约束 H01–H10。具体范围写入版本配置。
4. 改动后重建墙、开口、角色通路与拓扑，先检查H01–H10和默认开口/大小间要求，再进入Depthmap与战斗评价。局部合法不代表全图合法。
5. 优先局部修复，最多 8 轮。确认违规记为 INVALID，程序错误按 ERROR 处理并重试同一请求。无变化的子代保留重复记录并计入预算。修复范围仍受声明的区域和接口约束。
6. 为每个候选保留父代、实际操作/参数前后值、结构检查结果和见证路径。展示修复前后差异；原来为Seed 6保留的蓝圈分区是固定回归样例，不应把该坐标复制成所有seed的强制布局。新子代遵循形态规则，已批准回归样例本身继续受保护。

#### 3.3.4 验收与数据解释

Phase 2按固定100seed重新统计每项结构限制通过率、不同房数/基础拓扑/环数及全部失败，保留原>=80%/5种房数/10类拓扑/3种环数目标；所有正式合法候选都必须满足保护规则，不用平均分抵消违规。抽取至少12张覆盖窗户、多门、大小间和L形的布局做Godot实际机制检查；编辑器切seed、重开和运行必须对应同一Layout。人工审阅正反例和已锁分区单列，不能当作独立样本或缓存命中重复验收。

当前外壳方案已获得人工布局确认并通过 Phase 2 校准准入，证据见 [SHELL_PHASE2_ACCEPTANCE](reports/combat_v3/SHELL_PHASE2_ACCEPTANCE.json)。单局路线用于设计解释和待验证假设，不硬性规定玩家走原路线、停留时长、死亡位置、Choice/Gate Counts目标或战斗节奏。Phase 3评价与校准这些规则下的地图，不能为高分放宽用户确认的形式与通道语义。

## 4. 评分协议、证据和防刷分

硬约束先于软分：几何、通路、碰撞、净空、门角色规则、出生、补给可达、合法伤害/拾取、相同固定资源预算，排除敌人不能反制的永久安全射击位置。理论弹药伤害要足够；是否已有获胜证据单独表示。统一状态VALID／INVALID／UNCERTAIN／ERROR，并附具体原因；ERROR不能当低分地图，UNCERTAIN不能当已证明无解。

四目标0–100越高越好，最小化`[-S,-F,-P,-D]`：

| 主分 | 子项与内部权重 |
|---|---|
| S：战斗空间结构质量 | 全局真实空间指标分布50%，功能区域指标分布50% |
| F：公平性与资源 | 获胜率目标适配50%，反应余量25%，补给可获取性25% |
| P：压力与视域节奏 | 有效威胁35%，有效射击窗口30%，丢失/重获目标20%，换弹/拾取风险15% |
| D：有效战术多样性 | 成功路线差异35%，交战位置分布25%，替代路径实际使用25%，破坏后的战术变化15% |

展示总分`Q=0.15S+0.35F+0.30P+0.20D`，不参与遗传生存选择或掩盖硬约束。旧结构距离另命名保留，绝不与新版S混用。S比较空间组织和功能，不比较坐标/外轮廓。Connectivity用可见点比例，Metric除以可玩面积平方根，Integration保留定义并用固定基准尺度比较分布；初始与全开分开计算。功能类别由几何/实际连接复算，不能仅改标签降损失；Gate Counts和Convex Choice校准前排除。统一网格与基准尺度，不逐候选各自归一化。

F的标准代理胜率50%–80%仅为待校准初始设计区间，高胜率不直接等于不公平。反应余量=从可感知威胁到攻击命中的时间-代理反应及合法躲避时间。补给按需要时是否安全取得评估。P按合法路径、攻击条件和破坏时间计算压力，不以隔墙直线距离或单纯靠近代替；射击窗口需相机可见、枪口畅通、瞄准/射击时间足够且仍能转移。D按固定米制网格、成功路线和真实替代路径计算，不能靠拆房间、开无用门或无限绕圈刷分。潜行者分裂前后分别报告；缺阶段、早死、零机会、少量胜利都按事前规则记录，不删失败局、不造零值、不从不同个体拼冠军。

每个子指标必须有变量/公式、单位、采集、有效范围、最优区间、惩罚/归一化、权重、缺失/极端处理、手算例和测试。区间型可用`q(x)=100 max(0,1-distance(x,[L,U])/τ)`。所有权重、阈值、尺度、终止、样本门槛与配置在正式搜索前冻结，变动新开实验。反例覆盖永久安全输出、无反击狭区、补给死锁、零伤害绕圈、穿墙/透视、早死分母漏洞、无意义拆房和缺第二阶段高分。人工样例不等于模拟数据。

### 4.1 校准、搜索与最终测试隔离

Phase 3在冻结前建立三类用途清单：校准集用于公式、阈值和代理调整；搜索使用已冻结的策略与场景；最终测试使用预先登记、未用于调参的场景种子、起点和能力配置。保存用途、来源、种子派生、Genome/Layout哈希及版本，不只依赖不同文件名区分数据。

对校准地图、独立布局测试集与搜索输出做精确重复、拓扑同构和近似几何重合审计，提前规定分组/隔离规则，记录无法避免的重合与结论限制；不得仅为消除重合而改变正式请求、补抽或预算。最终候选在原布局上使用未见场景复核属于预期重用，单独标明，不能误称为完全未见地图泛化。

最终测试只用于冻结后的报告。若依据其结果修改公式、代理或参数，该测试集已成为开发数据；修订须新建协议/实验ID并另设未参与调整的测试，保留原结果。追加复核及校准预算单列，不混入6048正式请求或12局搜索分数。

### 4.2 Python与Godot一致性验收

当前 Phase 3 校准由 Godot 的游戏场景统一执行交互、批量战斗和固定输入重放。Python 负责调度、证据校验与评分，旧代理用于早期记录复算。新批次标注 Godot 执行版本与实际物理频率。评分器仅接收经验证的测量，缺少的威胁、反应或行为多样性证据按 UNCERTAIN 处理；原有正式评价冻结条件继续生效。

Phase 2准备同一Layout、初态和可重放输入的配对验证样例，包含常规、极限通道、视线边界、门破坏和战斗事件边界。Phase 3在正式搜索前逐项比较导航/碰撞、实际视线、命中对象、伤害/弹药、拾取、Portal状态、分裂、终止原因与胜负；基于事件证据比较，不只对照总分或画面。

离散规则事件及结果必须一致；位置、时间与路径长度允许误差须结合固定逻辑步长和校准实测，逐项写出单位、容差、样本量及超限比例门槛，并在冻结前固定。不得在看到正式结果后放宽门槛。记录所有不一致、原始日志、差异归因及修复/复测结果；不能重放或未覆盖的部分明确列为未验证。

若出现穿墙命中、资源错误、非法通行、分裂/胜负规则冲突等严重差异，Phase 3门槛不通过；正式运行中发现此类问题应停止提交后续评价，保留检查点和已完成证据，修复后按哈希/协议规则决定恢复或新建实验，不把系统错误当低分地图。

### 4.3 S分解释与收敛报告边界

S表示对基准空间组织特征的适配，不自动表示更有趣或体验优于原作。最终同时呈现结构差异、战斗证据与独立验证；不为追求单一基准相似度而临时压缩拓扑探索范围或调整已冻结权重。

每代除S/F/P/D、展示Q与Pareto外，同时显示可行率、约束违反原因及程度（适用时）、重复率、修复/回退统计和拓扑多样性。超体积沿用事先固定的尺度与参考点，当前代与累计档案分开；代表个体分数允许波动，不承诺每一代或每个目标单调提高。正式运行仍按约定Generation 0–20和预算完成，不因事后观察曲线而提前停止或额外追加请求。

### 5.3 Phase 4 两代工程试跑

已完成 §5.3 原定的四步试跑：登记固定配置、接通 shell Genome 与局部算子、运行遗传与随机对照、核对恢复及固定输入回放。两组共享 8 个初始布局，各执行两轮、每轮 8 次新请求，合计 **48 次请求**，上限 576 局。实际评价 39 张唯一布局、468 局 Godot 战斗，遗传组有 10 个合法子代改变了实际房间邻接。

两组共用三种 paced 策略，每种使用场景种子 0–3。补给位置在房间重建时按同一规则确定。初始布局种子与原始快照哈希见 [试跑配置](configs/shell_pilot_v1.json)。全部请求、修复记录、亲缘、Pareto、同尺度父子图、Seed 1102 的诊断回放和复现命令见 [试跑报告](reports/combat_v3/PHASE4_SHELL_PILOT.md)。

### 5.4 Phase 4 正式引擎与单种子验收

**新外壳进化采用单亲档案方案。** 每个子代只记录一个真实亲代。新实验低频安排档案参考编辑，按种群的约 10% 确定尝试名额，每代至多为种群数除以 10 后向上取整。参考布局来自已提交且评分完整的历史档案，参考 ID 单独记录。每次只借用一个小间的角位，在亲代的母区内重建隔墙与开口。通过几何、角色通路和区域邻接检查后标为加号。借用失败保留原因，并沿用同一亲代继续常规编辑。借鉴 ShinkaEvolve 的历史档案抽样、局部编辑、较大重排和谱系回溯。候选由现有约束与可复现的算子生成，评价继续由 DepthmapX、Godot 和固定评分程序执行。已完成的双亲 v2 作为历史试跑。 [参考论文 §3、图 4](https://openreview.net/pdf?id=lKEdGCoDNC) · [历史试跑证据](reports/combat_v3/PHASE4_BREEDING_V2.md)

1. **抽亲代。** 从历史已提交代里收集通过硬约束、四项评分完整的布局，按 Layout 哈希去重。合法但未留在当代种群的个体仍可抽到。工程试跑采用权重 `w = 1 / [r × (1 + n)]`，其中 `r` 是 S/F/P/D 在抽样池的 Pareto 层级（从 1 开始），`n` 是该布局此前已提交的子代请求数，包含失败与重复。每代开始锁定抽样快照，记录亲代 ID、层级、请求数和随机种子；抽样池为空时记录原因并暂停。正式前按试跑验证并冻结抽样与编辑概率。
2. **编辑、评价与生存选择。** 按 §3.3.3 做局部编辑或区域重排。先检查几何、通路与重复，再送合格新布局去 Depthmap 和 Godot。当代种群用 S/F/P/D 非支配排序和拥挤度保留。记录全部请求、幸存种群、当前／累计 Pareto、展示代表、各目标历史最优、亲代、操作、修复和错误。原子写入完整代，验证固定种子重建、并行一致性与中断恢复。
3. **谱系 Viewer。** 显示真实地图和唯一亲代线。原始鼠王关 DXF 在顶部显示为三角形 Initial，以蓝色点线标出 G0 初始种群的生成来源。G1 起按实际归档中的亲代分叉排布，优先使用斜直线，必要时绕开无关节点。所有节点用同样大小的正方形外接框，G0 和区域重排用正方形，局部编辑用圆形，新单亲档案的成功参考编辑与历史双亲档案的交叉均用加号形。两类档案各自显示图例。单亲加号节点只有一条正式亲代关系，参考 ID 在详情中显示。缩略图各自等比例适配轮廓。谱系可双轴平移、缩放和复位。红叉只标确认无效，合法但未入选用中性标记，暂时没有后代的有效节点正常显示。证据不足、系统错误和重复分别列状态。Q 保留单色 0–100 外框。在显示范围内，从完整评分个体中分别选出 S、F、P、D、Q 的最高分，并列按出现 ID 稳定排序。四项主分用粗体字母，Q 用星标。各项谱系沿实际亲代着不同颜色，共用亲代线时并行显示，Q 路线最粗。标记和谱系高亮均用于展示。保留逐代回放、状态与 Pareto 筛选、父子与跨代同尺度对照、拓扑、证据和 Godot 重建。
4. **先验收单亲版两代。** 用独立运行 ID 和单列预算记录 G0–2，覆盖两类真实编辑、唯一亲代、历史有效个体可再抽、无效与合法未入选的区分，以及真实祖先回溯。用同一初始布局和锁定战斗参数核对固定种子、并行、缓存与恢复，报告实际拓扑变化、抽样分布与失败原因。
5. **单种子正式验证。** 通过 §5.2 和本节工程检查后，完成 Generation 0–20。初始 32 张，加 20 轮各 32 次请求，共 **672 次候选评价请求**。核对房间增删、邻接变化和新的非同构拓扑，输出统一比例的逐代 PNG、父子差异图、射击／死亡／补给／视域分布、破坏和分裂前后状态，以及由真实快照生成的 GIF／MP4。标出样本量和分母。

### 5.5 Phase 5 正式对照、消融与独立验证

| 组别 | 方法 |
| --- | --- |
| A | Legacy 固定拓扑＋原混合变量遗传算法。适配同一战斗协议，适配受限时报告不可比项。 |
| B | Full-PCG＋§5.4 单亲档案进化。 |
| C | Full-PCG＋独立随机采样，与 B 共用 Genome 初始分布、生成族、修复与评价。 |

- **预算。** 三组各跑三个种子，每次 672 个请求，共 **6048 次候选评价请求**。每次都执行 12 局时，理论上共 72,576 局。无效、重复及缓存命中照计请求。系统 ERROR 恢复同一请求。消融与额外复核使用独立预算。
- **统计。** 报告请求数、唯一 Genome／Layout、实际模拟局数、Depthmap 调用、缓存、修复成本、CPU 与墙钟时间，并以共同 CPU 时间截点比较。结果涵盖合法率、战斗支持率、拓扑多样性、S/F/P/D、固定尺度与参考点下的超体积、当前及累计档案、独立能力验证的稳定性。
- **验证。** 消融优先分别去掉 S、P、D，仍记录完整指标。至少选取 12 张覆盖不同房数、拓扑、特殊通道的合法候选做 Godot 实际穿门、射击、导航和战斗检查。三种子提供初步重复性证据。游戏体验结论由真人试玩另行验证。

## 6. 自动运行与最终交付

统一入口目标如下。各命令的实现和验收状态在进度文件中登记。

```text
python -m full_pcg generate --config ... --seeds 1:100
python -m full_pcg experiment --config ... --resume
python -m full_pcg export --run ... --figures --gif --mp4
python -m full_pcg verify --run ...
```

调度由本地程序独立运行，保留日志、超时、有限重试、缓存、原子检查点和配置版本校验。在冻结协议中确定 Godot 全量或抽样验证范围。各阶段的正式运行从原始日志到评分、从 Genome 重建到图件都要可追溯。

### 6.1 正式实验前的耗时与资源试跑

- 用 Phase 4 小批量试跑覆盖有效／无效候选、冷缓存／命中、不同房数与复杂度。分别测量几何、Depthmap、模拟、选择和保存的耗时，报告样本数、中位数、可估计的尾部耗时、并发、进程内存和磁盘／日志增长。
- 用实测的缓存率、失败率和并发估算 6048 次请求的墙钟时间及磁盘范围，注明有限样本的不确定性。资源不足时调整并重新试跑。
- 正式运行前锁定超时、重试次数、资源上限、磁盘不足／写入失败处理和进度告警。验证异常保留证据并可恢复。试跑单列 ID 与预算，正式运行按冻结配置和恢复规则执行。

### 6.2 代表地图集与最终证据包

- **选图。** 搜索前固定代表集的数量、选择、去重和并列规则。覆盖不同的目标取舍、房数、拓扑和特殊通道，复用 Phase 5 的 Godot 验证。缺项如实说明。按预定规则保留搜索高分但独立复核失败的诊断样例，有无均注明。
- **单图证据。** 同版本的 Layout／Genome、个体和父代 ID、运行 ID 与代数、S/F/P/D 子项及原始日志索引、独立复核和 Godot 验证状态、统一比例二维图及实际行为录像。没有录制时注明。
